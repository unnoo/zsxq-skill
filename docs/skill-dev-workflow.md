# Skill 开发工作流

在 zsxq-skill 里**新增或修改**一个「原子操作」或「场景」时遵循的标准生命周期。模板细节（reference 小节顺序、场景 10 节、frontmatter、安全规则）以 [`../CLAUDE.md`](../CLAUDE.md) 为唯一来源，本文档不重复；它负责把这些散落的约定**串成阶段**、给出每阶段的**退出判据**，并补上 CLAUDE.md 缺失的一环——**验证协议**（测试用例、真实输出、可提交的验证报告与原始日志）。

> 面向所有 agent（Claude Code、Codex、Cursor、OpenClaw 等），文中 "Claude Code" 泛指当前所用 agent。

## 何时用

- 新增 / 修改一个原子操作（`references/<domain>-<verb>.md`）
- 新增 / 修改一个场景（`references/scenarios/<scenario-id>.md`）

两者走**同一条五阶段生命周期**，只在两处分叉：**实现**阶段套用的模板不同（reference 模板 vs 场景 10 节）；**验证**阶段测试粒度不同（操作＝逐命令；场景＝逐分支 / 停止条件端到端）。分叉点在下文各阶段内标注。

## 五阶段总览

```
① 理解  →  ② 设计  →  ③ 实现  →  ④ 验证  →  ⑤ 验收收尾
   ↑                                    │
   └──────── 实测推翻假设则回到设计 ──────┘
```

| 阶段 | 一句话目的 | 退出判据（满足才进下一阶段） |
|------|-----------|------------------------------|
| ① 理解 | 摸清 CLI 真实能力与现有文档，不基于陈旧假设动手 | 已确认目标命令 / 接口真实存在，且现有文档未覆盖或需修改 |
| ② 设计 | 确定归为操作还是场景、落到哪些文件、写入类的安全边界 | 文件清单、操作/场景归类、写操作的确认项都已想清 |
| ③ 实现 | 按 CLAUDE.md 模板写 / 改文档并在 SKILL.md 注册 | 文档结构合规、SKILL.md 四处注册齐全（见下）|
| ④ 验证 | 用**真实运行**校准文档，产出可提交的报告 + 日志 | 验证报告结论为「通过」或「有条件通过」，日志已留存 |
| ⑤ 验收收尾 | 跑静态校验、提交、把验收材料交到用户面前 | `check-docs.py` 通过、已提交、已向用户呈现验收清单 |

## ① 理解

- 先跑最小只读命令确认能力真实存在：`zsxq-cli <domain> +<verb> --help`，或对未封装接口 `zsxq-cli api list` / 一次只读 `api call` / `api raw --method GET`。**不要**基于「CLI 大概支持」直接写文档——本仓库有过「文档按猜测写输出、实测才发现不符」的教训。
- 读现有相关 reference / 场景，判断是**新增**还是**修改**。
- **退出判据**：目标命令或接口在真实 CLI 上被确认存在（或确认「CLI 侧已登记、文档按可用写」这一显式决定并记录到设计里）。

## ② 设计

- **归类**（用 CLAUDE.md 的判据）：表达业务目标且需组合 ≥ 2 个独立操作 → 场景；否则 → 原子操作。查 ID、确认内容、验证结果是操作的前后置步骤，不单独算场景。
- **列文件清单**：要新增/改动的 reference、场景入口、SKILL.md 注册点（Shortcuts/API/原始 HTTP 表、快速索引、场景表、frontmatter description）。**每条路径对照 CLAUDE.md 的架构图验证目录层级**——场景脚本放 `skills/zsxq/scripts/scenarios/<id>/`，子文档放 `references/scenarios/<id>/`，静态资源放 `assets/scenarios/<id>/`；不要凭感觉把 `scripts/` 放到项目根。
- **读 vs 写**：判断是只读类还是写入/删除类——决定 reference 用哪种小节模板、是否需要 `> [!CAUTION]`、以及**验证阶段是否要走测试授权门**。
- **写操作的安全边界**：这一步就想清楚「执行前要向用户确认哪些项」（写进 CAUTION）、以及验证时用哪种安全测试策略（见 ④）。
- **退出判据**：文件清单 + 操作/场景归类 + 写操作确认项均已确定。复杂改动建议先把清单讲给用户过一遍。

## ③ 实现

按 [`../CLAUDE.md`](../CLAUDE.md) 的模板落地，不在此重复模板内容：

- 操作 → 「Reference doc 统一模板」（读 / 写两套小节顺序）+ 「Adding a New Operation」的注册步骤
- 场景 → 「场景 10 节」+ 「Adding a New Scenario」的注册步骤
- 错误分层：通用错误归 `auth-errors.md`，只在 reference 写该命令**特有**错误 + 末尾 fallback 一行
- **退出判据**：文档小节顺序合规；写入类有 CAUTION；SKILL.md 四处（对应表 / 快速索引 / 必要时 description / 场景表）注册齐全。

> ⚠️ 此时文档里的「输出」「错误说明」可能仍是**基于理解的初稿**。它们必须在 ④ 用真实运行校准后才算数——**严禁**把未经实测的输出示例当作最终版交付。

## ④ 验证（本工作流的重点）

目标：用**真实运行**证明文档写的命令、输出、错误、失败语义都对，并把过程沉淀成**用户可独立验收**的两份产物：

- **验证报告** `docs/verification/<id>.md` —— 可读摘要：测试用例、预期 vs 实际、校准了哪些假设、结论。用户读它验收。
- **原始日志** `docs/verification/logs/<id>.log` —— 可核底稿：命令原样、完整输出、退出码。用户拿它逐条核对报告。

`<id>` = reference 文件名去扩展名（如 `topic-attached-columns`）或场景 id（如 `archive-topics-to-column`）。

### 测试用例怎么设计

- **操作**：逐命令覆盖——正常路径、每个关键参数、已声明的每条特有错误、失败语义。读操作直接跑；写操作见下。
- **场景**：端到端覆盖——主干流程跑通一次，且**每条「分支与停止条件」都要有一个用例**（如「星球名命中多个」「专栏找不到」「N>30 翻页」「限流退避」），确保停止点真的会停。
- 每条用例记：**意图 → 执行的命令 → 预期 → 实际（真实输出摘录）→ ✅/❌**。

### 读操作

直接逐命令运行，把真实输出摘录进报告、完整输出进日志。**用真实字段校准文档的「输出」「参数」「说明」节**——发现文档与实际不符，回到 ③ 修文档，并在报告「实测校准」里记一条。

### 写操作（create / edit / reply / answer / delete / nps / tags / digest / 设置类）

写操作会改动真实数据，**必须**按序过三道关：

1. **测试授权门**：执行任何写入前，向用户取得**一次性明确授权**，并把授权来源记进报告「授权」栏。授权仅限本次验证范围，不顺延到其它写操作。
2. **选一种安全测试策略**（按优先级）：
   - **dry-run**：命令自带 `--dry-run` 时首选，不产生真实写入。
   - **自复原（net-zero）**：读原值 → 写测试值 → 复原原值，全程净零变更。适合可整表回设的操作（如 attached_columns、tags）。报告须写明如何保证净零、并**复原后再读一次**验证已还原。
   - **测试星球 / 测试对象**：在专用测试星球或一次性测试主题上操作，不碰生产内容。
3. **执行并记录**：按选定策略跑，报告记结论，日志记全过程（含复原步骤）。

> 若用户此前有「不要测试发布 / 写入类功能」的约束，则写操作验证**默认不执行**：报告标注「未执行实测，原因：用户约束」，并降级为「有条件通过（写路径未实测）」。仅当用户对该操作给出一次性授权时才执行。

### 能力缺失时：测降级路径，别把整个功能标「未实测」

当运行环境缺某项能力（如无 Playwright MCP 无法截图、无某 CLI 子命令、外部服务不可达），**不要把整条功能路径笼统标成「未实测」**——那会把「环境真的测不了」和「其实可测但我跳过了」混成一句话，正是让用户验收时看不清边界的根源（本仓库迁移 `generate-daily-poster` 时就犯过：把 HTML 生成、降级兜底和 Playwright 截图一起标未实测，实际前两者本地可测）。正确做法：

1. **把路径拆到「可测 / 不可测」的最小粒度**：一个依赖缺失的功能，通常只有末端那一环真不可测，其前置与兜底往往是本地/只读操作、完全可测。
2. **缺失能力时，它的降级 / 兜底路径几乎总是可测的，且必须测**——因为当前环境正是该兜底的触发条件（没浏览器 → 正好验证「保留 HTML」兜底）。兜底测不过比主路径缺失更危险。
3. **报告里分行呈现**，不合并：可测部分给真实用例与 ✅/❌；确实不可测的那环单列「未实测（原因：能力缺失 X）」，并写明**补测条件**（需要什么环境）。结论用「有条件通过（仅 X 未实测）」，而非笼统的「未实测」。

### 日志协议（强制，防掩盖失败）

这次开发中 429 限流曾被 `&& echo ok` 掩盖成「静默成功」。为杜绝此类，日志**必须**：

- **命令原样记录**，一条一段；**token 等凭证脱敏**（替换为 `<TOKEN>`），其余不改写。
- **完整输出照录**，成功与**失败都要记**，不截断关键部分。
- **每条命令记退出码**（如 `[exit 0]` / `[exit 1]`）。
- **禁止** `&& echo ok`、`|| true`、`2>/dev/null` 等任何掩盖失败或吞掉错误输出的写法。
- 报告里每段「实际输出摘录」都应能在日志中找到对应原文。

### 退出判据

- 报告结论为「通过」或「有条件通过」（写路径受约束未测时用后者并注明）。
- 报告与日志都已写好；实测发现的文档偏差已回改并在「实测校准」记录。

## ⑤ 验收收尾

1. 跑静态校验：`python3 scripts/check-docs.py`（死链、场景 10 节、写入类 CAUTION、写操作报告缺失提示等），修到通过。
2. 提交：文档改动 + 验证报告 + 日志一并提交。**开源仓库：功能确认完成前不开 PR（含 draft），只 commit + push 分支。**
3. **向用户呈现验收清单**（见下），把「读什么就能验收」直接递到面前，不让用户翻工具日志。

### 交给用户的验收清单

完成时用这一段收尾，让用户一眼可验收：

- 改了哪些文档（操作 / 场景 + SKILL.md 注册点）
- 验证报告路径 `docs/verification/<id>.md` —— 测试用例数、通过 / 失败数、校准了哪些假设
- 原始日志路径 `docs/verification/logs/<id>.log` —— 供逐条核对
- 写操作用了哪种安全策略、授权来源、是否净零复原
- `check-docs.py` 结果
- 未覆盖 / 已知风险
