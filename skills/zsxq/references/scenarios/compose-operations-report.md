# 运营报告（compose-operations-report）

把星球一段时间的运营情况整理成报告。三种变体共用一套原子操作与执行骨架：**日报**、**周报**（都需确认后发布到星球）、**复盘**（偏内部分析，默认不发布）。**写入类步骤（发布报告、加精）执行前必须停下向用户确认。**

## 适用意图

- 「帮我做「星球名」今天的运营日报」
- 「做「星球名」本周（X 至 Y）的运营周报」
- 「帮我复盘「星球名」过去 7 天的运营情况」
- 每天/每周向成员同步内容动态、精选推荐、未答提问；训练营或活动期间同步进度
- 每周复盘、给团队同步运营情况、判断内容方向是否需要调整

## 不适用情况

- 只想看某段时间发了哪些主题、不需要整理成报告 → 直接用 [group-topics](../group-topics.md)
- 只想查未答提问、不做报告 → 直接 `api call get_self_answer_topics`（见 [SKILL.md](../../SKILL.md#主题管理topic) API 表）
- 想按关键词/话题聚合内容 → 用 [topic-search](../topic-search.md) 或 [group-hashtags](../group-hashtags.md)
- 只想把某几条主题设精华、回答某个提问 → 属单一原子操作，见 [topic-digest](../topic-digest.md) / [topic-answer](../topic-answer.md)

## 所需输入

| 输入 | 必填 | 说明 |
|------|------|------|
| 星球名称或 group_id | **是** | 只给名称时先 `group +list` 定位 ID；名称命中多个时列候选让用户确认 |
| 变体 | **是** | 日报 / 周报 / 复盘，决定时间窗、分析项与是否发布 |
| 日期范围 | **是** | **必须由用户明确给出**，不要让 AI 自行判断"今天/本周"以免时区或跨天偏差：日报给某天（如 `2026-07-28`，窗口 = 当天 00:00 至现在）；周报/复盘给开始与结束日期（如 `2026-07-22 至 2026-07-28`） |
| 选题/加精数量 | 否 | 周报选题建议默认 2–3 条；复盘加精候选默认 3–5 条 |

## 使用的原子操作

| 操作 | reference | 在本场景中的作用 |
|------|-----------|-----------------|
| `group +list` | [../group-list.md](../group-list.md) | 过渡步骤：按星球名定位 group_id |
| `group +topics` | [../group-topics.md](../group-topics.md) | 按时间窗拉主题，统计数量/类型分布；JSON 输出的 `counts` 直接提供点赞/评论数 |
| `topic +detail` | [../topic-detail.md](../topic-detail.md) | 对选出的热门 / TOP 主题取完整正文并核对互动数据 |
| `api call get_self_answer_topics` | [../../SKILL.md#主题管理topic](../../SKILL.md#主题管理topic) | 拉「别人向我发起的提问」，`topic_filter: "unanswered"` 取未答清单 |
| `topic +create` | [../topic-create.md](../topic-create.md) | **写入**：确认后把日报/周报发布到星球 |
| 分享链接拼接 | [../share-links.md](../share-links.md) | 周报热门内容附主题链接 |

## 执行流程

三种变体共用第 1–3 步（拉数据），在第 4 步按变体分析，第 5 步整理稿件，第 6 步按变体决定是否发布。

### 第 1 步：定位星球与确定时间窗（共用）

1. 用户只给星球名时，先 `group +list` 拿到 group_id；命中多个相似星球时列出候选（group_id + 名称）让用户确认，不默认取第一个
2. 把用户给的日期范围换算成时间窗 `[窗口起点, 窗口终点]`：
   - 日报：起点 = 指定日期 00:00，终点 = 现在
   - 周报 / 复盘：起点 = 开始日期 00:00，终点 = 结束日期 23:59（复盘常用"过去 7 天至今"）

### 第 2 步：拉时间窗内主题并统计（共用）

用 `group +topics --group-id <id> --json` 按时间倒序取主题。**`--end-time` 只是上界游标，没有下界参数**，窗口起点靠客户端按 `create_time` 自行截断：

1. 取第一页；逐条比较 `create_time`，保留 ≥ 窗口起点的主题，丢弃更早的
2. 若整页都还在窗口内且 `has_more: true`，用返回的 `next_end_time` 作为 `--end-time` 翻下一页，直到某条 `create_time` < 窗口起点即停止翻页
3. 对窗口内主题按 `type` 统计：`talk`（帖子）/ `q&a`（提问）/ `task`（作业）/ `solution`（作业答案）各几条，以及总量
4. JSON 每条主题自带 `counts`（`comments` / `likes` / `readers`），排热门时**直接用列表里的 `counts`**，无需逐条拉 detail

> 类型名以 CLI 实际输出为准：只有 `talk` / `q&a` / `task` / `solution` 四种，**没有"文章"类型**。报告概览按实际存在的类型列，不要照搬含"文章"的模板。

### 第 3 步：拉未答提问（共用）

`api call get_self_answer_topics --params '{"topic_filter":"unanswered","count":<n>}'` 取「别人向我发起、我尚未回答」的提问。

- 该接口是**跨星球**的，返回项带 `group` 字段：按当前星球 group_id 客户端过滤，只留本星球
- 再按 `create_time` 落在时间窗内筛选（日报=今天、周报/复盘=本周）
- 需要更多时用返回的 `next_end_time` 作为 `end_time` 翻页

### 第 4 步：按变体分析

**日报**
- 从第 2 步窗口内主题里，按 `counts.likes` / `counts.comments` 选出最高的 1–2 条作为"今日热门"
- 对这 1–2 条可选 `topic +detail` 核对完整正文与互动数，供摘要用
- 汇总今日待办：结合未答提问与热门讨论，给 1–3 条操作建议

**周报**
- 按互动量（点赞 + 评论）排出 TOP 3 主题；对 TOP 3 逐条 `topic +detail` 核对互动数据并取正文摘要（主题多时这步稍慢，属正常）
- 未答提问：本周全部列出
- 根据本周高频话题/类型分布，给下周 2–3 个选题建议
- 每条热门主题用 [share-links](../share-links.md) 拼接主题链接（电脑端 + 手机端）

**复盘**
- 内容概览（总量 + 类型分布）+ 未答提问清单
- 从本周主题里挑 3–5 条适合加精的优质内容（高互动 / 高价值 / 未加精 `digested: false`），每条给推荐理由
- 汇总"需要星主决策的问题"（如某提问该谁回、某内容方向是否调整）

### 第 5 步：整理成稿（共用）

按变体套用手册格式（概览用第 2 步真实类型分布；数字来自真实统计），生成完整稿件，**先展示给用户**：

- 日报：`📋 运营日报 · [日期]` — 今日新增 / 待回复提问 / 今日热门（👍💬）/ 今日待办
- 周报：`📊 运营周报 · [日期范围]` — 内容概览 / 本周热门（按互动排序，附链接）/ 未答提问 / 下周选题建议
- 复盘：`📊 运营周报 · [日期范围]` — 内容概览 / 待处理提问 / 本周优质内容推荐（含理由）/ 下周选题建议

### 第 6 步：确认后发布（日报 / 周报）

- **日报 / 周报**：用户看稿后明确说"发布"，才用 `topic +create --group-id <id> --text "<稿件>"` 发到星球（写入前确认见[用户确认点](#用户确认点)）；发布后可 `topic +detail` 验证
- **复盘**：默认**不发布**，把报告交付给用户即可；若用户要求把复盘也发到星球，走同样的发布确认流程

## 分支与停止条件

- **未定位到星球 / 名称命中多个**：列候选让用户确认，不猜
- **时间窗内无主题**：如实报告"该时间段无新增主题"，日报/周报仍可出（概览为 0、无热门），不虚构内容
- **无未答提问**：报告"无待回复提问"，正常继续
- **翻页到窗口外**：某条 `create_time` < 窗口起点即停止，不继续翻更早的页
- **主题量大 / detail 逐条慢**：周报 TOP 3 才逐条拉 detail，其余用列表 `counts`，避免全量拉详情
- **限流（429 / frequently）**：退避几秒重试，不循环猛刷
- **复盘中遇需确认的写入操作**（如加精、回答）：暂停，告知用户再继续，不擅自执行

## 用户确认点

1. **发布日报 / 周报前**（`topic +create` 写入）：确认稿件已成终稿，且确认目标星球（group_id + 名称）与正文内容 —— 用户明确说"发布"后才执行（见 [topic-create](../topic-create.md) 的 `> [!CAUTION]`）
2. **复盘默认不发布**：如用户要求发布复盘，同样先确认稿件与目标星球
3. **复盘中的加精 / 回答等写入**：只给候选与建议，是否执行由用户逐条确认（见 [topic-digest](../topic-digest.md) / [topic-answer](../topic-answer.md)）

## 完成标准

- 日报 / 周报：生成符合格式的稿件并经用户确认；用户说发布后 `topic +create` 成功、返回新 topic_id（未要求发布则交付终稿即完成）
- 复盘：交付含内容概览、未答提问、加精候选（带理由）、下周选题建议的报告，并标注需星主决策事项；默认不发布
- 报告中的数量、类型分布、互动数均来自真实拉取的数据，非估算

## 失败与回退

- **只读阶段（第 1–5 步）**部分失败（某页拉取出错、detail 超时）：从最后成功的 `next_end_time` 续拉即可，数据可重新累积，无副作用
- **发布阶段（第 6 步）**：`topic +create` 写入失败即原子回滚，不会留下半成品主题（见 [topic-create](../topic-create.md) 失败语义）；稿件仍在，修正后可重试发布
- 通用错误（401、404、参数缺失、`--end-time` 解析失败等）见 [auth-errors](../auth-errors.md#常见错误处理)
