# 提问管理（manage-inbound-questions）

集中处理**别人向星主发起、但星主还没回答**的问答类提问：拉取未回答提问 → 按优先级排序 → 逐条起草回答 → 用户确认后提交。**起草和排序阶段不写入；只有用户逐条确认后才提交回答，且每题只能回答一次、无法修改。**

## 适用意图

- 「帮我找出别人向我提问但我还没回答的问题，整理一下」
- 「把待回答的提问按优先级排一下，给我回答草稿」
- 「集中清理一下我的提问箱/未回答的问答」
- 直播、活动、课程后积压了一批提问，需要批量整理再回复

## 不适用情况

- 用户想看的是**自己向别人发起**的提问（我问的、等别人答）→ 用 `api call get_self_question_topics`，不是本场景的 `get_self_answer_topics`（详见「使用的原子操作」的关键区分）
- 只想对某一条已知 `topic_id` 的提问直接回答 → 直接用 [topic +answer](../topic-answer.md)，无需整场景编排
- 想发普通评论而非"官方回答" → 用 [topic +reply](../topic-reply.md)（`+answer` 每题仅一次，`+reply` 可多条）
- 想统计/回顾**已回答**记录 → 同一工具传 `topic_filter:"answered"`，只读，不涉及本场景的提交环节

## 所需输入

无必填输入（工具自动作用于当前登录账户收到的提问）。可选：

- 拉取数量（默认最近 20 条）
- 优先级判定补充标准（如"这期训练营相关的都算 P1"）
- 用户最终标注**哪几条要提交回答** —— 提交前必须由用户给出

## 使用的原子操作

| 操作 | reference | 在本场景中的作用 |
|------|-----------|------------------|
| `api call get_self_answer_topics` | 无独立 reference（在 [SKILL.md](../../SKILL.md) 主题管理 API 表登记，参数 `topic_filter` / `count` / `end_time`） | 列出别人向当前用户发起的提问，用 `topic_filter:"unanswered"` 筛未答 |
| `topic +answer` ⚠️写入 | [topic-answer.md](../topic-answer.md) | 对指定 `topic_id` 提交官方回答；每题只能回答一次、不可修改 |
| `topic +detail`（可选） | [topic-detail.md](../topic-detail.md) | 提问引用了某主题、需补充上下文时按需拉取 |

**关键区分**：本场景用 `get_self_answer_topics`（别人**向我**提问、等我答）。**不要**误用 `get_self_question_topics`（那是**我向别人**提问、等别人答）—— 两者参数相同，方向相反，用错会拉到完全不相干的列表。

## 执行流程

### 第一步：拉取未回答提问

```bash
zsxq-cli api call get_self_answer_topics --params '{"topic_filter":"unanswered","count":20}'
```

从返回 `topics_brief[]` 的每条提取：

- `topic_id` —— 后续提交回答的目标1
- `content` —— 提问正文，用于生成"提问内容摘要"
- `group.name` / `group.group_id` —— 来自哪个星球
- `create_time` —— 提问时间
- `owner.name` —— 提问者（辅助起草，不在输出列中）
- `type` —— 应为 `q&a`

顶层 `has_more` 为 `true` 时可用返回的 `next_end_time` 作为下一次 `end_time` 继续翻页；默认只取最近一批。

### 第二步：按优先级排序

对每条提问打上优先级：

- **P1 高**：涉及付费体验 / 课程 / 退款 / 活动兑现（影响已付费用户的核心权益）
- **P2 中**：多人可能关心的共性问题（答一次能惠及多人、可沉淀成公开内容）
- **P3 低**：个人化问题，或星球内已有类似回答

用户补充的判定标准优先于上述默认规则。

### 第三步：逐条起草回答草稿

为每条提问撰写 **200 字以内**的建议回答草稿。若提问引用了某主题或需要更多上下文，可对该 `topic_id` 用 [topic +detail](../topic-detail.md) 拉详情后再起草。草稿此刻只是文本，**不提交**。

### 第四步：输出整理清单，等待用户标注

按下列格式汇总，交用户确认：

| 优先级 | 提问内容摘要 | 来自哪个星球 | 提问时间 | 建议回答草稿（≤200 字） |
|--------|--------------|--------------|----------|--------------------------|

**到这里为止不做任何写入。** 请用户标注要提交的条目（以及需要改写的草稿）。

### 第五步：逐条提交回答（需用户确认后）

仅对用户标注的条目，按 [topic +answer](../topic-answer.md) 逐条提交：核对 `topic_id` 与最终回答文案 → 提交 → 记录结果 → 下一条。未标注的提问保持未回答，不动。

## 分支与停止条件

- 未回答提问为空 → 报告「当前没有待回答的提问」，结束
- 提问数量超过一批（`has_more:true`）→ 说明还有更多，询问是否用 `next_end_time` 继续拉取，默认只处理最近 20 条
- 返回项 `type` 非 `q&a`（异常）→ 该条不适合 `+answer`，跳过并在清单中标注
- 遇限流（429 / `frequently`）→ 退避几秒重试，不循环猛刷
- 用户只要整理清单、暂不回答 → 第四步结束，不进入提交

## 用户确认点

`topic +answer` 是**公开写入**，且**每题只能回答一次、回答后无法修改**（见 [topic-answer.md](../topic-answer.md) 的 `> [!CAUTION]`）。因此：

1. **不得批量一次性提交**；对用户标注的每一条，提交前逐条确认「目标 `topic_id` + 提问内容 + 将要发布的回答全文」
2. 只提交用户**明确标注**的条目；未标注的一律不提交
3. 草稿经用户改写的，以用户最终确认的文案为准

## 完成标准

- 用户标注要回答的每条提问都已成功提交官方回答，或已明确跳过
- 未标注的提问保持未回答状态，未产生任何写入
- 向用户回报：已提交的条目（`topic_id` + 所属星球）、跳过/失败的条目及原因

## 失败与回退

- 逐条提交、彼此独立：某条失败不影响其他条。
- `topic +answer` 写入失败即原子回滚，**不消耗**"每题一次"额度，核对参数后可对该条重试（失败语义见 [topic-answer.md](../topic-answer.md)）。
- 若提交时报 `问题已回答`（他处已答或并发），说明额度已用尽，无法再答，跳过即可。
- **已成功提交的回答不可撤销、不可修改** —— 这是确认环节必须充分的原因；续跑时只对尚未成功的条目重试，不重复提交已成功项。
