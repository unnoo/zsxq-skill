# 自动打标签（batch-tag-topics）

对星球最近一段时间的新主题批量分析内容，对照一组**给定的候选标签**自动推荐，星主统一确认后批量回标。**设置标签是覆盖式写入：`titles` 为主题的完整标签集合，会覆盖原有标签；批量执行前必须先并入每条的原有标签，并把全部方案一次性列给星主确认。**

## 适用意图

- 「获取星球「X」最近一周的新主题，看看适不适合「A」「B」「C」「D」这几个标签，每条推荐 1–2 个，没合适的不推；批量设置前先列给我确认」
- 「用这几个固定标签给最近的帖子批量回标」
- 「新增了标签体系，帮我把最近这批内容按这些标签归类打标」
- 业务目标：在**固定候选标签集**内对一批主题做自动推荐 + 批量回标，提升分类效率。

## 不适用情况

- 只给单条主题打标签 → 直接用 [topic-tags](../topic-tags.md) 原子操作，无需场景编排
- 还没有确定的候选标签，需要从内容里"发现"该建哪些标签（常与加精一起做）→ 用 [curate-digest-and-tags](curate-digest-and-tags.md)（精华与标签整理，从零发现加精 + 标签候选）。本场景只在**已给定**的候选集内回标
- 只想按已有标签浏览 / 筛选内容（不是打标）→ [group-hashtags](../group-hashtags.md)
- 想改动标签体系本身（重命名 / 删除星球标签）→ 不在本场景范围

## 所需输入

- **星球**：名称或 `group_id`（只给名称时先 `group +list` 查 ID）
- **候选标签集合**：一组标签标题（如 A / B / C / D）。本场景只在此集合内推荐，不自创集合外的新标签（除非用户明确允许）
- **时间窗**：默认"最近一周"，可改（如最近 3 天 / 本月）
- **每条推荐上限**：默认 1–2 个，可调
- 可选：是否允许"无合适标签则不打"（默认允许，宁缺毋滥）

## 使用的原子操作

| 操作 | reference | 在本场景中的作用 |
|------|-----------|-----------------|
| `group +list` | [../group-list.md](../group-list.md) | 星球名称 → `group_id` |
| `group +topics` | [../group-topics.md](../group-topics.md) | 拉时间窗内的新主题；`--json` 一次带回 `content`（供内容分析与原有标签解析），`--end-time` 作翻页游标 |
| `topic +detail` | [../topic-detail.md](../topic-detail.md) | （按需）单条复核内容与现有标签 |
| `set_topic_tags` | [../topic-tags.md](../topic-tags.md) | **写入**：批量回标；`titles` 为完整标签集合（覆盖式） |
| 分享链接拼接 | [../share-links.md](../share-links.md) | 为确认清单生成主题链接 |
| `group +hashtags` | [../group-hashtags.md](../group-hashtags.md) | （可选）核对候选标签在星球是否已存在 |

## 执行流程

### 第一步：确定星球与参数

- `group +list` 拿到 `group_id`；名称命中多个时列出候选（`group_id` + 名称）让用户确认，不默认取第一个
- 与用户敲定：候选标签集、时间窗、每条推荐上限、"无合适则不打"策略

### 第二步：拉取时间窗内的新主题（只读）

- `group +topics --group-id <id> --json`，结果按时间倒序（newest-first）
- 时间窗为**客户端过滤**：只保留 `create_time >= 截止时间`（截止 = 当前时间 − 时间窗）。`--end-time` 是向更早翻页的游标，不是下界
- 当 `has_more: true` 且当页最后一条仍落在窗口内时，用返回的 `next_end_time` 作 `--end-time` 继续翻页；一旦某条 `create_time` 越过截止时间即停止
- 每条记录 `topic_id` / `title` / `content` / `create_time`

### 第三步：分析并推荐标签

- 逐条阅读 `content`，在候选集内挑 1–2 个最贴合的标签；不贴合则不推
- 不自创候选集外的标签

### 第四步：解析每条主题的"现有标签"（覆盖式关键）

- `set_topic_tags` 是**覆盖式**——提交的 `titles` 即主题最终的完整标签集合
- 现有标签内嵌在主题 `content` 里，形如 `<e type="hashtag" hid="..." title="%23...%23"/>`：`title` 为 URL 编码、首尾带 `#`。解析方式：对 `title` 做 URL 解码、去掉首尾 `#`，得到原有标签名（`set_topic_tags` 的 `titles` 不带 `#`）
- **最终 `titles` = 原有标签 ∪ 本次推荐（去重）**。任何一条只要带有原有标签，就必须并入最终集合，否则打标时会被抹掉

### 第五步：生成确认清单

- 每条列出：主题前 10 个字 · 链接（[share-links](../share-links.md) 拼接）· 现有标签 · 推荐标签 · **合并后最终 `titles`**
- 汇总一次性列给星主，等待确认（见"用户确认点"）

### 第六步：确认后批量执行（写入）

- 逐条调用 `set_topic_tags`，`titles` 用第四步合并后的完整集合
- **节奏控制**：逐条串行、条间留小停顿，不并发猛刷；遇限流（429 / `frequently`）退避几秒重试
- 记录每条成功 / 跳过 / 失败

## 分支与停止条件

- 星球名称命中 0 个或多个 → 让用户确认目标，不默认取第一个
- 时间窗内无主题 → 报告"无新主题"，结束
- 全部主题都无合适候选标签 → 报告"无推荐"，不做任何写入
- 主题量偏大（如数十条以上）→ 提示用户缩短时间窗或分批处理
- 限流（429 / `frequently`）→ 退避几秒重试；连续失败则暂停并报告已完成进度
- 某条无权限修改标签 → 跳过并在清单标注（见 [topic-tags](../topic-tags.md) 错误说明）

## 用户确认点

1. **星球有多个命中**：确认目标 `group_id` 后才继续
2. **批量写入前统一确认（本场景核心）**：把完整清单（每条 主题前 10 字 · 链接 · 现有标签 · 推荐标签 · **合并后最终 `titles`**）一次性列出，星主确认后才批量执行——不要边分析边打标
3. **显式标出标签差异**：凡会改动某条原有标签集合的，在清单中标出"现有 → 最终"的对比，让星主确认不会误删原标签
4. 允许星主逐条否决或调整推荐后再执行

## 完成标准

- 时间窗内每条待处理主题：要么已按"合并后完整 `titles`"成功打标，要么被明确跳过（无推荐 / 无权限 / 用户否决）
- 已打标主题的原有标签均被保留，无因覆盖被抹掉
- 向用户报告：成功条数、跳过条数及原因、失败条数

## 失败与回退

- `set_topic_tags` 单条失败即该条不改变原标签（见 [topic-tags](../topic-tags.md) 失败语义），不影响其他条 → 可对失败条重试
- 批量中途中断可续跑：已成功的无需重做，对未处理条重新走"解析现有标签 → 合并 → 设置"
- 若某条被错误覆盖（如漏并原有标签），用同一命令把正确的完整 `titles` 再设一次即可纠正（覆盖式的双刃）
- 无逐条自动回滚——第五步的确认清单是防误删的主要保障，务必先确认再批量执行
